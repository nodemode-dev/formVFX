# backend · HASHOUT_LOG

Living context for the engine service. Code carries almost no comments; the reasoning lives here.

## Shape

- `app/engine/host.py` owns the one `fvx_core.Engine` on a dedicated thread (the engine is not `Send`). Everything that touches it is submitted as a callable to that thread; a 100 ms tick drains engine events, polls background jobs and autosaves.
- Frame, audio and thumbnail renders are built on the engine thread as `FrameJob` / `AudioJob` / `ThumbJob` snapshots (an `Arc` of the project) and run on thread pools with the GIL released, so rendering never blocks editing.
- `changed` events go to every window over the bus with `revision`, `edited` (did the project change, which purges RAM previews) and `source`. Commands that do not bump the revision (time.set, layer.select) still publish with `edited: false` so every window follows the time and selection.
- `app/engine/rpc.py` is the single JSON-RPC dispatcher behind `/api/rpc`, the `/api/live` socket, the MCP tools and the CLI. `engine.batch` takes `$N.key` references counted from 1.

## Agent substrate

- `app/agent/tools.py`: the MCP tools and the guide texts. The tool catalogue is the source the harness skill's `references/tools.md` is generated from (`./formvfx agents sync`).
- `rpc.execute` (0.23.0) clears the cached effect catalogue after any `effect.plugins.*` command, because a loaded plug-in adds an effect the catalogue did not have.
- `run_script` (0.22.0) sends `script.run` with the code and returns the engine's `{ok, result, output, error}` as it is, so an agent sees `$.writeln` output and the failing line without a second call. A script is one undo step and asks for consent like any other change.
- Consent (`app/agent/consent.py`): a per-boot token in the Terminal panel's environment marks trusted agents; others ask once in a window (Allow, Allow Always, Don't Allow) unless `FORMVFX_AGENTS` is `allow` or `deny`. Reads never ask.
- `app/agent/workspace.py` writes the agent workspace (`~/Formvfx/agent-workspace`): CLAUDE.md, AGENTS.md, MCP configs for the three clients, a `formvfx` shim on PATH and the harness skill.
- `app/agent/stdio.py` is the stdio relay `./formvfx mcp` runs: it finds the engine (FORMVFX_URL, the discovery record, the default port) and starts one headless when none answers.

## Facts that bit

- Unknown parameters in `execute` are ignored by the engine, not rejected.
- `prop.set` takes menu values as 0-based indices only; option names fail.
- Giving a vec3 transform property two values sets z to 0 (scale z 0 matters once a layer turns 3D).
- Keyframe commands (`prop.addKey`, `keys.set`, `keys.select`) take layer seconds; `set_keyframes` converts and snaps.
- `layer.newText` positions are baselines.

- Query commands (`_QUERY_IDS` in `app/agent/consent.py`) never touch the revision; when the interface sends one, `rpc.execute` also skips `host.note`, so viewer polling (`track.status`, `puppet.info`) stays out of the Activity list. Agent queries are still logged.

- `/api/peaks/{item}` (0.4.0): the engine thread only builds the job (`peaks_job`, cheap); the summary runs on `host.jobs`. Results are kept by the job's key (footage path, or comp id and revision) in an LRU of 48, and concurrent requests for one key share one task. 204 when the item has no audio.
- `ui.flowchart` is a read RPC; agents get the same graph through `get_comp {flowchart: true}` (layers and effects included).

- Multi-frame rendering (0.5.0, `app/engine/performance.py`): `performance.json` in the data folder keeps `multiFrame` and `reservedCores` (default 0). At start the engine sets `RAYON_NUM_THREADS` to the cores left (unless the variable is already set), which also sizes the engine's Render Queue batches; that part applies at the next start. Previews follow at once: `/api/viewer` range requests keep up to `host.preview_frames` frame jobs in flight and send them in order; a new single-frame request cancels the window and the range resumes from its first unsent frame. Keep `reservedCores` at 0 by default: one reserved core on a two-core machine halved single-frame speed, because every frame's own pixel work shares the same rayon pool.
- `/api/snapshot.png` serves the Take Snapshot image (`snapshot()` on the engine); 204 when there is none.
- `render_frame {view}` renders a 3D comp from a 3D view through the frame job's `view3d` parameter.

- Text preset library (0.6.0, `app/engine/text_presets.py`): `presets/text-animators.json` is generated by `setup/text_presets.py` (edit the generator, then `./formvfx presets`; CI runs `--check`). It is read once from the repository root, or from the frozen bundle's `presets` folder (`--add-data presets` in both freeze scripts). `text.library` lists it without animators; `text.applyLibraryPreset` sends the whole preset object to the engine's `apply_text_preset`, after turning `#n` layer references into ids through `comp.info`, because the engine only takes ids and names.
- `apply_text_preset` and `paste_svg` go through `_native_edit`: the call is made with `touches=True` so the revision moves and the interface pulls, and `host.note` records it in Activity like a command.
- Curl Noise Generator (0.7.0) is the engine's `fx.noise.curlNoise`: a velocity grid (curl of fractal Perlin noise, step up to 8 px) and a line integral convolution over a white-noise texture, f32 in the inner loop; about 1.3 s for a 1920 x 1080 frame on two cores.
- `capabilities()` reports `effects.total` for the whole catalogue, the hidden effects (Paint, Roto Brush, Face Track Points) included; the Effects and Presets panel lists the rest.
- `track.planar` (0.7.0, `planar_corner_pin` on the engine): optional `track.mask {method: perspective, wait: true}` runs forward from the reference (start) and backward to it (end); the mask path keys give a homography per frame (least squares over vertices and tangent ends), then each frame is rectified through it and re-aligned to the reference frame (KLT on Shi-Tomasi features inside the mask, RANSAC homography, two passes, a correction over 40 px is refused). Error on a synthetic clip fell from 1.6 px mean, 5 px worst (frame to frame) to 0.2 px mean, 0.6 px worst. The corners become a Perspective tracker (keys on featureCenter and attachPoint) and `tracking::apply` keys the Corner Pin. Corner Pin does not pad its buffer, so the pin is clipped to the target's own bounds: a Grow Bounds sized to the farthest corner goes in front of it. The guide mask is set to mode None.
- GPU (0.8.0): the engine's wgpu compositor is in the default build. `Host.attach_gpu` runs on the engine thread at start and when Settings changes it: if `FORMVFX_GPU` allows and `performance.json` has `gpu: true`, `performance.gpu_probe()` returns the cached probe for this core version and platform (`gpu-probe.json`) or runs `formvfx_engine.py --gpu-probe` (the frozen exe with `--gpu-probe`) in a child process with a 90 s limit, so a driver that crashes takes the probe down, not the engine. Only a probe that opened a device lets `Engine.set_gpu(True)` attach the accelerator; `host.gpu` is what `engine.info`, `engine.performance` and the MCP `status` report. The engine keeps the opened device, so turning the GPU off and on does not open a second one. Frame jobs take `backend: auto|gpu|cpu` (default auto: the engine measures both per comp and uses the faster; a project on Mercury Software Only stays on the CPU). On Mesa's software Vulkan the GPU frames match the CPU within 1 of 255 and are slower, so Auto keeps light comps on the CPU there.
- Object Matte (0.9.0): `roto.objectPreview` builds an `ObjectJob` on the engine thread (`object_job`: project, footage and cache handles, the layer, the point in layer pixels, the time) and runs it on `host.jobs`: it loads MobileSAM once per process from the installed weights (checked against the registry's SHA-256), renders the layer's source frame, embeds it (MobileSAM keeps the last embedding, so a second point on the same frame only decodes, about 0.1 s against 2.5 s for the first) and returns the mask at no more than 256 px a side as alternating run lengths (off first), its origin and step in layer pixels, a bounding box, the coverage and the model's IoU estimate. It is a read in `_READ_RPC`. `roto.objectMatte` selects MobileSAM if it is installed and not active, then runs `roto.stroke` (a 3 px foreground dot at the point) and `roto.span` (the whole layer; `$1.effect` from the stroke) in one `engine.batch` labelled "Object Matte", then `roto.propagate` both ways (`wait` optional).
- Square-shaped range selectors do not move with `offset`: a library reveal keys `start` (in) or `end` (out) instead. Ramp Up with offset -100 to 100 reveals; Ramp Down with the same keys hides.
- Dynamic Link (0.10.0, `app/engine/link.py`, `app/routers/link.py`): `GET /api/link/info`, `/api/link/frame.png` and `/api/link/audio` take `project` (an `.fvxproj` path) and `comp` (id or name). With no project, or the project open in the window, they read the live engine, unsaved edits included. Any other project is opened in a side engine (its own `fvx_core.Engine` on its own thread, never ticked, so it never autosaves; the session has no config store, so it writes no settings and no recovery sentinel), reopened when the file's mtime changes, at most two kept (least recently used dropped). The routes need the `x-formvfx-local: 1` header on GET as well, since `LocalOnly` only asks it of writes, and they refuse any path that is not `.fvxproj`, `.ecproj` or `.ecprojx`. `link.export` (RPC, the `dynamic_link` MCP tool, the Project panel menu) writes `<project> - <comp>.fvxlink`, a JSON descriptor (`formvfx.link/1`: project, comp id and name, size, rate, duration, URL templates) and needs a saved project. `link.info` is a read.

## The engine module

- `app/native.py` imports `fvx_core` (`native/fvx-core`) once per process. `native.module()` is what `host.py`, the Dynamic Link side engines and the self-check import, so nothing else names the module. `native.engine_name()` is `fvx`; `engine.info` carries the engine's own `capabilities()` (`engine`, `projectExtension`, `importProjects`), which the interface reads to name its save dialogs.
- Engine commands that cannot do something yet raise a sentence ("... is not in formvfx yet"); the RPC layer passes it through like any command error.
- `.ecproj` and `.ecprojx` projects from earlier formvfx releases open as imports; saving always writes `.fvxproj`.

## Extensions (0.28.0)

- `routers/extensions.py` serves an installed CEP extension's files at `/api/extensions/[folder]/[path]`. The folder must be one `extensions.list` reports, and the resolved path must stay inside it. HTML pages get the host runtime object and `CSInterface` shim injected after `head`, so a panel that ships its own `CSInterface.js` still finds the bridge it calls; `/api/extensions/_csinterface.js` serves the fallback alone for panels that load it by path.

## Embedded Claude Code and Chat (0.30.0)

- `app/agent/claude_code.py`: finds the Claude Code CLI the way a packaged app must, since a GUI app gets a minimal PATH: `FORMVFX_CLAUDE_BIN`, PATH, `~/.claude/local`, `~/.local/bin`, npm, bun and volta folders, Homebrew and `/usr/local/bin`, then `$SHELL -l -c 'command -v claude'`. `argv` (terminal) and `headless` (Chat) pass the formvfx MCP server inline over HTTP with the per-boot `x-formvfx-agent-token`, so Claude Code connects with no project approval step and is trusted; `--allowedTools mcp__formvfx ToolSearch` and the system note `NOTE`. On POSIX the command runs through `$SHELL -l -c exec ...` so the person's PATH applies. `child_env` drops `CLAUDE*` variables except the four credential and config ones.
- The note names ToolSearch with the exact `select:` query because Claude Code defers MCP tools: without it the agent fell back to Bash and the `formvfx` shim.
- `routers/terminal.py`: `Session` takes an optional argv; the socket's `agent=claude` (with `prompt`, `resume`) spawns Claude Code as the PTY's process instead of typing `claude` into a shell, which failed whenever `claude` was not on the GUI PATH. `status` reports `claude` from `claude_code.info()`. Codex and Cursor still launch by name in the shell.
- `app/agent/chat.py` and `routers/chat.py` (`/api/chat/state|claude|send|cancel|reset`): one headless `claude -p --output-format stream-json --verbose --include-partial-messages` turn at a time on a daemon thread, `--resume` with the session from `system/init`; publishes `{"type": "chat", "kind": user|start|init|delta|tool|toolDone|usage|done|reset}` to windows over the bus. Subagent events (`parent_tool_use_id`) and the ToolSearch chip are skipped; 200 messages kept in memory.
- `routers/mcp.py`: `tools/list` and `prompts/list` carry `LIST_CACHE` (`ttlMs`, `cacheScope`) under protocol 2026-07-28. Claude Code 2.1.300 rejects a 2026-07-28 list result without them (`Invalid result for tools/list: ttlMs expected number`) and then shows no formvfx tools at all: this was why Claude Code did not connect, over HTTP and over the stdio relay alike.

## Dynamic Link robustness (0.36.0)

- `engine/link.py` `resolve(project, uid, hint)`: the open project wins (`live`, also when only its project id matches); then the path itself (`direct`, if its id agrees or either has none); then a search of the `.fvxlink`'s folder (`hint`, the `link` query parameter), the project's old folder, the open project's folder and the folders of `recent.json` (the engine's recent projects in the data folder), first by project id (same file name preferred, then newest), then by file name (`relinked`). Nothing found raises "no project at ... moved or renamed and was not found in <folders>", which the router turns into a 404. `_peek_uid` reads a `.fvxproj`'s `uid` and caches it by mtime.
- `_comp_params`: a comp id that no longer exists in that project falls back to the comp's name (`compName`), so a renumbered comp still resolves.
- Descriptors (`export`) now carry `formvfx` (the writer's version), `projectId`, `compName` placeholders in the frame and audio URLs, and the `check` and `render` endpoints. Older descriptors (no `projectId`) still work by path and file name.
- `check(descriptor, path, write)`: refuses a link whose `formvfx.link/N` is newer than this build reads, with the writer's version in the message; warns when the writer's version differs or the comp's width, height or frame rate changed; with `write` and a path, rewrites the `.fvxlink` to the resolved project and comp.
- `render(descriptor, output, fmt)` (Render and Replace): opens the resolved saved project in a side engine (never the window's project, so its Render Queue and undo stay untouched), adds the comp to that engine's queue and renders with `wait`; output defaults to `<project> - <comp> (rendered).<ext>` beside the project. A live project with unsaved changes gets a warning that the render uses the saved file.
- `_log` keeps the last 60 link events (kind, project, comp, ok, relinked or error, message, resolved path); `status()` returns them with the side engines. Routes: `GET /api/link/status`, `POST /api/link/check`, `POST /api/link/render` (body `link` or `path`); `info`, `frame.png` and `audio` accept `projectId`, `compName` and `link`.
- `agent/tools.py` `dynamic_link` gains the `check`, `render` and `status` actions (path is the `.fvxlink`).
- Export does not save the project. A project opened before 0.36.0 has its id in memory only until its next save, so a link exported before that relinks by file name rather than by id.
- Known gap: when the window's own project file is moved while it is open, links keep resolving to the open project (live), but Render and Replace needs the saved file and fails until the project is saved again.

## Tabbed terminals and Chat like formlit (0.46.0)

- `app/agent/terminals.py` is the terminal session manager: `Session` has an id, title, kind (shell, claude, codex, cursor), its argv and env, a 256 KB scrollback and a set of asyncio queues. One reader thread per spawn owns the pty fd and closes it when the program ends; `gen` makes a restarted tab ignore its old reader, and a reaper thread waits on the child so nothing stays a zombie. Kill is SIGHUP and SIGTERM to the process group, then SIGKILL after 1.5 s if still alive. Sessions live in the engine process (`atexit` closes them), not in any window.
- Every output chunk carries a sequence number; a socket attaches under the session lock and takes the scrollback plus the sequence it covers, then drops queued chunks at or below it, so a reconnect replays without duplicating or losing output.
- `routers/terminal.py`: `GET /status|/list`, `POST /open|/claude|/launch|/restart|/close`, and `WS /api/terminal/{id}/ws` (raw text out, `{"type": "exit"}` when the program ends; `{"type": "input", data}` and `{"type": "resize", cols, rows}` in). The old single `/api/terminal/ws` with query parameters is gone. `restart` clears the scrollback, sends `ESC c` to attached sockets and runs the same argv again; a socket stays attached across a restart. Blocking work (pty fork, the login-shell lookup for `claude`, `codex`) runs in the executor.
- `/claude` with a prompt and no `resume` types the prompt into a live Claude Code tab (Enter follows 200 ms later so it is not swallowed as part of a paste) and returns that tab; without a live tab, or with `resume`, or with no prompt, it starts a new tab through `claude_code.argv`. `/launch` runs `codex` or `cursor-agent` through the login shell with `exec`, resolved first so a missing program answers 400 "... is not installed on this computer" instead of opening a dead tab.
- `agent/claude_code.py`: `NotInstalled` (a `RuntimeError`) carries `INSTALL`, "Claude Code is not installed on this computer. ..."; the routers turn it into a 400. `headless(..., note)` takes the system note so Chat can add `CHAT_NOTE` (short Markdown, few tool calls) to the shared `NOTE`.
- `agent/chat.py` follows formlit's `cmd_chat`: the reply is `{role, parts: [text | tool], error, meta}` and lives in `messages` from the moment it starts, so `GET /api/chat/state` rebuilds a half-written answer after a reload. `usage` is `{input, output, costUsd, context, window, model}`; `context` is the last model call's prompt tokens (input plus cache reads and writes) taken from `message_start`, `window` comes from the result's `modelUsage[...].contextWindow` and, until the first result, is 200000 (1000000 for a `[1m]` model id). Events on the bus channel `chat`: `start`, `delta`, `tool` (input is a one-line JSON summary, 160 characters at most), `toolDone` (images a tool result carried are written to `~/Formvfx/Chat/<uuid>.<ext>` and sent as absolute paths for `/api/fs/file`), `usage`, `done` (error, meta, usage, session), `reset`, `adopted`. `STATE["run"]` is bumped by send, reset and adopt, so a stopped or orphaned reader thread cannot write into a newer conversation.
- `GET /api/chat/sessions` lists `*.jsonl` conversations under `$CLAUDE_CONFIG_DIR/projects/<agent workspace path with non-alphanumerics as "-">` newest first (twenty at most; files without a user question are skipped; the title is the first question with the trailing `[formvfx context: ...]` removed). `POST /api/chat/adopt {session}` replays the transcript into Chat (text, tool chips with error status, sidechains and synthetic messages skipped), sets the next `--resume` and the starting context from the last assistant usage.
- Terminal and Chat are plain routers; neither is an MCP tool, so `agent/tools.py` needed no exclusion list change.

## Cross-site requests with no Origin (0.51.8)

- Plan and ledger: the family agent-stack standard, rule G4 (`AGENT_STACK_STANDARD.md` v0.2.0, owner decision D4, ledger FB-035, formai_dev sidecar). `app/core/security.py` `LocalOnly` admitted a request with no Origin once its client and Host were loopback (`local_origin` answers true for no Origin), so a web page could make the engine answer a GET by pointing an `<img>` or a link at `http://127.0.0.1:<port>/...`: browsers send no Origin on those, and any GET route with a side effect would run.
- The rule: a request that carries no Origin header is refused (the existing 403, "Local API request refused") when `Sec-Fetch-Site` is `cross-site`, trimmed and case-insensitive. A request that carries an Origin is decided by `local_origin` alone. `same-site` stays allowed on purpose: a dev window on `localhost:5230` loading straight from `localhost:8230` is same-site, and no outside page can be same-site with localhost. The CLI, `setup/mcp_stdio.py` and Claude Code's MCP client send neither header and pass. `POST /mcp` keeps its own `local_origin` check. WebSockets always carry an Origin.
- Checked on the running engine (port 9124) at `/api/health`: no Origin with `cross-site` and with `  Cross-Site ` 403; `same-site`, `same-origin`, `none`, no header, and `cross-site` with the dev Origin `http://localhost:5230` 200; a foreign Host and `Origin: http://evil.example` 403. In Chromium, a page served from `http://127.0.0.2:9903` with an `<img>` and a clicked link pointing at `/api/health` got 403 for both, shown in the engine log. The built window served by the engine (`FORMVFX_DIST`) in Chromium at 4x CPU and slow network, two shift runs and one throttle run: no errors and no refusals from the window (6 refusals in the log before and after, all from the probes). Layout shift is 0.0106 (the Home screen's category row 0.0008, `SECTION.cv-home-section` 0.0089, the timeline search 0.0004, the document title 0.0005), the same 0.0106 on an engine run from the previous HEAD, so it does not come from the guard. `POST /mcp` initialize with no Origin 200; `setup/mcp_stdio.py` initializes and lists 27 tools. The compositing core was built here (`maturin develop --release`, fvx_core 0.51.7) to boot the engine.

## An Origin must be this app's own window (0.52.0)

- Plan and ledger: the family agent-stack standard, rule G2 (`AGENT_STACK_STANDARD.md` v0.2.0, ledger FB-038, formai_dev sidecar), as formwav 2.21.6 shipped it. `app/core/security.py` `LocalOnly` judged an Origin by its host alone (`local_origin`), so a page on any localhost or 127.0.0.1 port, such as `http://localhost:5230` (another form app's window), was answered.
- The rule: on the loopback path an Origin, when present, must be the engine's own (scheme http, host and port equal to the request's Host), `tauri://localhost`, `http://tauri.localhost` or one of `config.cors_origins()` (the dev and preview origins). `_origin_key` parses scheme, host and port (default 80 and 443) and the comparison is on the parsed tuple, never a prefix or the host alone. No Origin, the local header rule, G4, the Host check and the 403 body are unchanged. `local_origin` stays for `POST /mcp`, which sits behind `LocalOnly`. Note the CORS list names `localhost:5251` for the preview, not `127.0.0.1:5251`.
- Checked on the running engine (port 9161) at `/api/health`: `Origin: http://localhost:5230`, `http://127.0.0.1:9162`, `http://localhost.evil.com`, `http://evil.example`, `null`, `http://localhost:5250.evil.com` and `https://127.0.0.1:9161` 403; the engine's own origin (127.0.0.1 and localhost), the dev origin 5250, the preview origin 5251, `tauri://localhost`, `http://tauri.localhost` and no Origin 200; cross-site with no Origin and a foreign Host 403, cross-site with the dev Origin 200. `POST /mcp` initialize 200 and `setup/mcp_stdio.py` lists 27 tools. The built window served by the engine under 4x CPU and slow network: two shift runs and one throttle run, no errors, layout shift 0.0106 (as at 0.51.8), 12 refusals in the log before and after, so none from the window; the img and link probes from 127.0.0.2 are still 403.

## The test suite (0.52.2)

The tests run on the CPU path; a GPU render is not tested (no GPU in CI).

## Renders that outlive the request, and one engine per port (agent render reliability)

- A waiting `renderQueue.render` used to join the render thread inside `Engine.execute` on the engine thread with the GIL held, so the whole process stopped answering (health, the live socket, MCP) for the length of the render. A CLI whose 900 s request timed out then saw no healthy engine, started a second one, and that one failed to bind (`[Errno 48]`) and dropped its `Engine` on the main thread (`unsendable ... dropped on another thread`).
- Now `Engine.execute` releases the GIL while a command runs (the Rust engine is `Send`; the `unsendable` pyclass still pins the object to the engine thread), and `rpc.execute` turns a waiting render into a background one (`wait: false`) and polls `renderQueue.list` with `asyncio.sleep`, so the engine thread is free between polls. The render thread never depends on the request: a dropped client leaves it running. `render.status` is the read-only RPC that polls without writing to the Activity list.
- The Render Queue keeps the last 64 finished results (`finished` in `renderQueue.list`) because the tick's `export::poll` consumes them; a poller matches them by item id.
- The CLI never holds one long request for a render: `exec renderQueue.render` and `render --wait` start it in the background and poll `render.status` every second, printing progress on stderr. Ctrl+C leaves the render running (`render --status`, `render --stop`). The MCP `render` tool waits up to 10 minutes, below the stdio relay's 900 s timeout, then returns `running` with the next step.
- `client.engine_url` checks whether the port is held before starting an engine. A held port that does not answer health within 10 s is reported with the `lsof` line to find it; no second engine starts. `setup/serve` and `backend/boot_backend` refuse a held port before importing anything. `host._run` drops the `Engine` on its own thread at shutdown.
- CLI contract: `exec`, `batch` and `render` print `"ok": true` on success (added to object results that have no `ok` of their own) and `{"ok": false, "error": ...}` with exit status 1 on failure. A command's own `error` field (`prop.setExpression` reports the expression's error there, `null` when it compiled) is part of its result, not a failure.
- The `./formvfx` dispatcher `cd`s into the repository, so the CLI resolves relative render outputs (`output`, `path` on `renderQueue.*` and `render.*`) against `FORMVFX_CALLER_DIR`, the folder the person ran it from.

## Windows desktop build for formcompiler (0.52.4)

- `formvfx.bat desktop build` used to run `build_app.bat`, which installs everything again and takes no arguments, and `setup\desktop_build.bat` ran `tauri.cmd build` with nothing after it, so formcompiler's `--config` (the updater settings) never reached the Windows build and no updater files or `windows-x86_64` entry in `latest.json` were made.
- Now `formvfx.bat desktop build ARGS` calls `setup\desktop_build.bat %3` to `%9` (the same build, freeze and `tauri build` as `setup/desktop_build` on macOS and Linux), and `setup\desktop_build.bat` passes `%*` to `tauri.cmd build`. `build_app.bat` stays the one-shot local path (tools check, install, desktop install, build) and calls `setup\desktop_build.bat` with no arguments.
- `setup\freeze_backend.bat` stops on a failed copy or `--selfcheck` with `exit /b 1`, so `call setup\freeze_backend.bat || exit /b 1` in `desktop_build.bat` cannot miss a broken sidecar (a batch file that falls off its end does not reliably trip `||`).
- The sidecar is `src-tauri\binaries\formvfx-engine-<host triple>.exe` on Windows (`rustc -vV` host, or `FORMVFX_TARGET`), which is what Tauri's `externalBin` `binaries/formvfx-engine` looks for. The bash `setup/freeze_backend` adds `.exe` through `fx_exe` the same way.
- `.gitattributes` keeps every text file LF and checks the `.bat`, `.cmd` and `.ps1` files out with CRLF, so cmd reads labels and `goto` targets correctly on a Windows runner whatever its git settings, and Git for Windows never turns the bash scripts into CRLF.

## The window's scripts keep their types on Windows (0.52.5)

- Python's `mimetypes` takes file types from the Windows registry (`HKEY_CLASSES_ROOT\.js`, value `Content Type`) over its own table, and some installers and editors set `.js` to `text/plain`. On those PCs the engine served the built window's scripts as `text/plain`, WebView2 refused every module script under strict MIME checking, and the desktop window stayed blank; macOS, Linux, dev mode (Vite serves the page) and Windows PCs with the default value never showed it.
- `main.py` pins `.js` and `.mjs` to `text/javascript` and `.css` to `text/css` with three `mimetypes.add_type` calls, which covers `StaticFiles`, `FileResponse` and any direct `guess_type`. They sit after the last import, not above the imports: a module that re-reads the registry while importing cannot undo them, and no import follows a statement (E402). They look redundant off Windows; keep them.
- Repro on a Windows PC: `reg add "HKCU\Software\Classes\.js" /v "Content Type" /d "text/plain" /f`, then launch the rebuilt app; restore with `/d "text/javascript"`.
- Checked here: with the table poisoned to `text/plain` for js, mjs and css through `mimetypes.init(files=...)`, the three calls return `text/javascript`, `text/javascript` and `text/css`; `py_compile` passes. Not yet run on a Windows PC.

## Media plugins on Linux (0.52.5)

- Footage audio is decoded in the window (`frontend/src/engine/playback.ts`, AudioContext and decodeAudioData), which on Linux is WebKitGTK decoding with GStreamer. `src-tauri/tauri.conf.json` `bundle.linux` now follows formdeck: the deb recommends `gstreamer1.0-plugins-base`, `gstreamer1.0-plugins-good` and `gstreamer1.0-libav`, the rpm recommends `gstreamer1-plugins-base` and `gstreamer1-plugins-good`, and the AppImage bundles the media framework; formcompiler installs the base and good sets on the Linux runner so the AppImage step finds them.
- apt and dnf install recommends by default; `dpkg -i` and `--no-install-recommends` skip them. On Ubuntu 24.04 `libwebkit2gtk-4.1-0` already depends on base and good but only suggests `gstreamer1.0-libav` (the AAC and H.264 decoders), so the deb recommends it. The AppImage carries base and good only, since libav would copy the runner's own FFmpeg into the app.
- Checked: the config parses and formcompiler's `registry.py check` passes; no Linux build was run here.
